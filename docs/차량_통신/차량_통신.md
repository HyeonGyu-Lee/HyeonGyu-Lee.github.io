## 제어·sensor·진단 traffic을 network에 배치하는 상황


Protocol 선택은 속도만의 문제가 아니다. Topology, 중재·schedule, 오류 처리, 전원 상태와 hardware 비용이 각 traffic의 요구와 연결된다.


> 차량 network를 물리 계층·frame·상위 protocol·검증 관점으로 연결하는 학습 문서 모음이다.

### 문서 읽는 순서


물리 연결과 속도 → frame·접근 제어 → 신호·서비스 표현 → 진단·보안 → 검증 순서로 읽는다. 하나의 기술명만으로 실제 시스템의 전체 통신 구조를 설명할 수 없다.


### network 선택의 기준

- 데이터량과 갱신 주기, 허용 지연·지터.
- 케이블·커넥터·배선 비용, node 수와 topology.
- 고장 검출·복구, 실시간성 요구와 안전 관련 설계.
- 기존 ECU·도구·진단 환경과 호환성.
- 보안, 전원 상태, 확장성과 유지보수.

### 계층을 구분한 비교


CAN·CAN FD·CAN XL은 서로 다른 frame 특성과 호환 조건을 갖는다. LIN은 스케줄 기반 저속 network다. FlexRay는 시간 기반 통신을 포함한다. MOST는 멀티미디어 전송 맥락에서 읽는다.


Ethernet의 10BASE-T1S·100BASE-T1·1000BASE-T1은 물리 계층 규격이다. IP·UDP·TCP, SOME/IP, DoIP은 그 위에서 고려하는 서로 다른 계층의 protocol이다. TSN은 Ethernet에서 시간·스케줄·자원 관리를 다루는 표준 기능 모음이다.


### message를 읽는 두 관점


신호 기반: message ID와 신호 위치·스케일·단위·주기를 해석한다. 서비스 기반: 서비스·인스턴스·메서드·이벤트와 제공자·소비자 관계를 해석한다. 실제 시스템에서는 두 방식이 gateway를 통해 함께 사용될 수 있다.


### 학습 범위


아래 문서는 핵심 원리, 구성 항목, 분석·검증 시나리오를 제공한다. 실제 규범적 요구사항과 숫자 제한은 적용 규격 판·PHY·controller·프로젝트 사양으로 확정한다.


### network 설계 실습


예제 요구: 저속 액추에이터 4개, 주기 신호를 교환하는 제어 node, 대용량 데이터를 보내는 컴퓨팅 node가 있다. 액추에이터의 데이터량·응답 시간·wakeup 조건부터 정리하고 LIN, CAN 계열, Ethernet 후보를 비교한다. 요구사항 없이 특정 버스를 먼저 선택하지 않는다.


산출물은 node 목록, 연결도, message·서비스 목록, 지연 예산, 고장 시 동작표다. 정상 통신 외에 전원 재인가와 gateway 단절 상황을 표에 추가한다.


## 이 영역에서 다루는 관점


차량 통신은 ECU 사이의 message contract·주기·bus load·topology·physical interface·diagnostics·gateway·recovery 관점으로 읽는다. 같은 CAN/Ethernet이라도 MCU 내부 clock·register·buffer·DMA·driver 설정은 MCU Peripheral에 분리한다. OSP는 차량 조명 node의 제어 protocol로 이 영역에서 다룬다.
